# Verifiable Context Reuse for Multi-Turn Coding Agents: Visibility-Proof Delivery and Verified History Projection

**Manuscript draft v0.6** · Evidence frozen · No new model experiments  
**Target:** SCI Q4 journal (software engineering / applied AI / intelligent systems)

---

## Abstract

Multi-turn coding agents must resend a growing mix of workspace files and interaction history at every step, which inflates prompt cost and risks delivering stale or incomplete state to the model. Existing context-compression, truncation, retrieval, and memory-reuse methods reduce token usage, but they rarely verify that content intentionally omitted or reused is still visible—and version-consistent—in the *final* message list actually sent to the model. We study **verifiable context reuse** under two complementary mechanisms. First, **Visibility-Proof Selective Delivery (VSO)** checks, at the final-messages boundary, that every omission in scope is fully visible with a content hash matching the current workspace; on failure the system re-injects the file or fails closed and skips the model call. Second, **Verified History Projection (S1)** folds redundant complete `FILE` blocks in assistant history by normalized path, keeping the last complete block per path (and the first version under the *first_last* configuration used in our confirmatory runs), while preserving the visible-file mapping that VSO extracts. On a preregistered multi-task protocol with DeepSeek-v4.1-flash-1017 and qwen3-coder-flash (56 tasks × 7 arms × 3 repetitions = 1176 episodes per model), the projected configuration reduces mean prompt tokens per episode by **16.9%** (Δ = −632.6, 95% CI [−885.7, −403.5]) on DeepSeek and **18.6%** (Δ = −697.3, CI [−969.7, −446.7]) on Qwen relative to the selective-delivery baseline, while episode success-rate (ESR) differences remain within a −12 percentage-point non-inferiority margin (DeepSeek ΔESR = −1.2pp, CI [−5.4pp, +3.0pp]; Qwen +1.8pp, CI [−0.6pp, +5.4pp]). Controlled fault injection shows VSO detects unsafe omissions and falls back correctly in 30/30 phase-2 scenarios (unsafe ships = 0). Offline replay on 504 episodes / 2808 steps reports zero violations of projection preservation. Archetype-cluster bootstrap confirms that prompt savings and non-inferiority hold when tasks sharing design templates are resampled as groups. We claim neither universal safety nor KV-cache/latency gains: VSO’s guarantee is limited to in-scope omissions under controlled delivery faults, and S1’s preservation argument is constructive under a specified extractor semantics—not a formal proof over arbitrary message streams.

**Keywords:** multi-turn coding agents; visibility-proof delivery; context reuse; history projection; context compression; non-inferiority testing; fault injection

## 1. Introduction

Coding agents work in a read–edit–verify loop. At each step the prompt typically concatenates a system prompt, accumulated trajectory (including full file rewrites emitted by the model), and a snapshot of relevant workspace files. As steps accumulate, repeated full-file rewrites make prompt growth super-linear in trajectory length, and long-context degradation is well documented in both general and coding settings [1–5]. Dropping or summarizing history is therefore attractive: it lowers token spend and can reduce distraction.

However, *less context is not automatically safe context*. When a system omits, summarizes, or retrieves only part of the workspace, a necessary file version may never reach the model’s input. Failure modes include (i) content that was once sent but was later trimmed out of the final message list, (ii) hash mismatch between what the prover believes is visible and what is on disk, and (iii) silent loss of intermediate file versions that later steps still need. Compression methods that optimize token count without a delivery-side check leave this risk unaddressed; memory systems that store state outside the transcript do not, by themselves, prove that the *final* request body contains what the policy claims to deliver.

This paper asks a focused question:

> In multi-turn coding agents, how can we reduce redundant context transmission while verifying that selectively omitted or reused workspace content remains visible and version-consistent in the final model input?

We decompose the question into two mechanisms that operate at different layers of the same pipeline.

1. **Visibility-Proof Selective Delivery (VSO).** Before each model call, the system extracts full file bodies from the *final* messages (assistant `FILE` blocks and current-context file blocks), normalizes paths, and compares content hashes with the workspace. Omitted files must reappear in full with matching hashes; edit targets and candidate-full files must appear in the current context. Failures trigger re-expansion (re-injection) or fail-closed (no request). VSO does not claim that the system discovered *all* task-relevant information—only that objects *in scope for omission checks* satisfy visibility and version consistency at the delivery boundary.

2. **Verified History Projection (S1).** Assistant history often contains multiple complete rewrites of the same path. S1 keeps, for each normalized path, the **last complete `FILE` block** (and the first block under the *first_last* dial used in confirmatory runs), replacing earlier complete blocks with a fold marker that cannot be mistaken for a live `FILE` fence. Under the shared extractor used by VSO, this preserves the path→body map that phase-A proofs and phase-B checks consume.

We intentionally **do not** claim S1/S2 as standalone algorithmic innovations in the sense of novel data structures; the contribution is coupling delivery verification with a projection that is safe *relative to that verifier*, plus a preregistered evaluation protocol. A rule-based obligation ledger (S2) appears only as an optional reminder heuristic in full-system configs and is **not** a core contribution. Dual-token addressing was tested in a dedicated ablation and did **not** show independent benefit; it is excluded from the contribution list.

**Contributions.**

1. **VSO:** a final-messages visibility and version-consistency gate for selective delivery in multi-turn coding agents, with fail-closed behavior under controlled delivery faults.
2. **S1:** path-normalized projection of complete history `FILE` blocks that preserves the VSO-visible file map under a stated extractor semantics, with a constructive preservation argument and large-scale offline replay.
3. **Evaluation:** preregistered multi-arm experiments on two cloud LLMs (DeepSeek and Qwen) with mechanism ablation (no-projection vs. projection), external truncation/summarization/retrieval baselines, controlled VSO fault injection, and post-hoc archetype-cluster sensitivity analysis.

## 2. Related Work

### 2.1 Context Compression and Context Management

Token-level and extractive compressors (e.g., LLMLingua [14], Selective Context [15], lexical deterministic pipelines [16]) reduce prompt size for general LM workloads. For *agents*, AGORA [17] shows that token-level extractive compression can destroy action grammar and proposes step-granularity retention floors. ACON [ACON] optimizes context compression for long-horizon agents under memory and reasoning constraints. Recent measurement work stresses that compression changes information available to later decisions: Compact-Bench [Compact-Bench] isolates damage from history replacement in long-horizon coding agents; *Measure Before You Manage* [MBYM] evaluates heterogeneous working-memory objects in coding agents before proposing management policies; *Beyond Token Savings* [BTS] systematically varies what/when/how much to compress. FOCUS [FOCUS] targets decision-preserving training-free compression.

**Positioning.** These lines reduce *volume* or improve *what to keep*. None of them, as specified in the sources we verified, installs a **final-message, hash-checked delivery gate** that must pass before every model request when files are omitted. VSO addresses that delivery boundary; it is not a new compressor.

### 2.2 Agent Memory and Retrieval

MemGPT [6], Generative Agents [7], Reflexion [8], and Voyager [9] structure long-term or skill memory for LLM agents; surveys organize the design space [10, 11]. TrawMem [12] reports task-oriented workspaces with moderate context reduction; EvoMemBench [13] finds strong long-context baselines, motivating non-inferiority rather than superiority claims. Retrieval-augmented generation [RAG1, RAG2] and coding-agent retrieval benchmarks (ContextBench [22], related retrieval suites) measure *what to fetch*, not whether the *final* prompt still contains omitted-but-required state.

**Positioning.** Memory and retrieval decide *storage and selection*. VSO decides *whether the selected delivery is complete and consistent at send time*. S1 is a transcript-side projection, not an external memory store.

### 2.3 Coding Agents and Repository Context

SWE-bench [18], SWE-agent [19], AutoCodeRover [20], and OpenHands [21] define interfaces and repository exploration for issue resolution and general coding. ContextBench [22] treats context retrieval itself as an evaluation object. Workspace state and multi-turn edit traces interact: full rewrites in history dominate prompt growth when agents emit complete files.

**Positioning.** We evaluate on synthetic micro-repository multi-step edit tasks (not full SWE-bench), with prompt tokens and ESR as primary metrics. Our claims are about *delivery-verifiable reuse* under that protocol, not universal coding-agent superiority.

### 2.4 Verification and Safe Context Delivery

Prompt-cache auditing [24] and verified semantic caching (vCache [23]) verify *cache hit* correctness or side channels for inference serving. PagedAttention [25] and related serving work optimize prefill memory/latency—not agent delivery semantics. To our knowledge, the verified combination of (i) omission authorization against a visible-file map and (ii) a pre-send check on the *final* messages list, with fail-closed re-injection, is the specific gap VSO fills.

**Positioning summary.**

| Concern | Typical focus | This paper |
|---|---|---|
| Compress / truncate / summarize | Reduce tokens | Cost side (baselines + S1) |
| Retrieve / remember | Store or fetch state | External memory (not claimed) |
| Verify final delivery | Hash + visibility of omitted files | **VSO** |
| Project history safely | Keep verifier-relevant file map | **S1** |

We do not claim VSO is the first compression method or S1 the first history filter; novelty is the **coupling**, the **final-messages check**, and the **preregistered closed-loop evaluation**.

## 3. Method

### 3.1 Problem Formulation

Let a multi-turn episode proceed in steps \(t = 1,\ldots,T\).

- **Workspace** \(W_t\): mapping from normalized relative path \(p\) to file body \(b\) (and content hash \(h = \mathrm{SHA256}(\mathrm{norm}(b))\)).
- **History** \(H_t\): messages available before step \(t\) (system, prior assistant outputs, prior user context, etc.).
- **Final messages** \(\mathcal{M}_t\): the exact list submitted to the model API at step \(t\).
- **Omitted set** \(\mathcal{O}_t \subseteq \mathrm{dom}(W_t)\): paths the assembler chose not to re-send in full this step (subject to policy), which VSO must still account for if they are in check scope.
- **Edit targets** \(E_t\) and **candidate-full** \(C_t\): paths that must appear in the *current* user context (last user message) when checks apply.
- **Visible map** \(V(\mathcal{M})\): `full_files_in_messages` — scan assistant `FILE:` fenced blocks and current-style `--- FILE … ---` context blocks; assign by normalized path with **later messages overwriting earlier** ones (last-write-wins).
- **Context cost**: per-episode sum of prompt tokens (including auxiliary compressor prompt tokens when applicable).
- **Capability**: episode success rate (ESR) under a frozen step-level evaluator.

**Path normalization** \(\mathrm{norm}(\cdot)\) unifies separators and relative forms so that the same logical file maps to one dictionary key. **Complete `FILE` block**: an assistant substring matching a fence pattern with a path line and a closed code fence—not a truncated or malformed fragment.

### 3.2 Overall Architecture

Per step, the production path is (order taken from the implementation, not a redesign):

1. Trim / select history policy inputs; optionally apply **S1** projection to assistant `FILE` blocks in history (`project_history`).
2. Optionally render open-obligation reminder lines (**S2**, auxiliary only).
3. **Phase A:** build candidate proofs from the *projected* history via the same extractor `full_files_in_messages` (so proofs match what will be re-embedded).
4. Assemble current context (must / edit-target / candidate / related policy); build \(\mathcal{M}_t\).
5. **Phase B (VSO):** `verify_omissions_in_messages(\(\mathcal{M}_t\), \(\mathcal{O}_t\), disk hashes, \(E_t\), \(C_t\))`.
6. If check fails: force full re-injection of failing paths and rebuild; if still failing → `INSUFFICIENT` / fail-closed (**no model call**).
7. Gate `should_call_model`; only then invoke the LLM API.
8. Apply returned `FILE` blocks to the workspace; record step outputs.

S1 therefore runs **before** proof construction and final-message assembly; VSO runs **after** assembly on the concrete \(\mathcal{M}_t\).

### 3.3 Visibility-Proof Selective Delivery (VSO)

**Check object.** Paths the system has identified as omitted (or as edit-target / candidate-full), not an open-ended “all information the task might need” set.

**Checks (final messages).**

- For each \(p \in \mathcal{O}_t\): \(p \in V(\mathcal{M}_t)\) and \(\mathrm{SHA256}(V(\mathcal{M}_t)[p]) = h_W(p)\) (version consistency).
- For each \(p \in E_t \cup C_t\): \(p\) appears as a full file block in the **current** user context with matching disk hash (history-only visibility is insufficient for E/C).

**Failure handling.** Re-assemble with `force_full` on failing paths; re-verify. Persistent failure sets `insufficient` and blocks the request (fail-closed). Success allows the call.

**Scope limits (explicit).**

- Does **not** prove the system identified every task-required file.
- Does **not** prove full semantic preservation of prose/history outside checked files.
- Does **not** parse or validate arbitrary non-file messages.
- Does **not** eliminate races between check and HTTP send (no cross-process lock in our harness).
- Controlled injection results do **not** imply production natural-fault rates.

**Algorithm (sketch).**

```text
# Phase A (candidate proofs) — uses projected history H'
proofs ← full_files_in_messages(H')          # path → body; last-write-wins

# Assemble M_t under omission policy O_t, targets E_t, candidates C_t

# Phase B (pre-send)
V ← full_files_in_messages(M_t)
for p in O_t:
    if p ∉ V or SHA256(V[p]) ≠ disk_sha[p]: FAIL
for p in E_t ∪ C_t:
    if p not fully visible in current user context with disk hash: FAIL
if FAIL: rebuild with force_full; recheck; if still FAIL: skip model call
else: allow model call
```

### 3.4 Verified History Projection (S1)

**Why history `FILE` blocks are redundant.** Full-file rewrites at each edit step restate entire files; intermediate versions of path \(p\) remain in the transcript even when later steps only need the latest body for delivery proofs.

**Why project by path, not by message length.** Visibility extraction is path-keyed with last-write-wins. Dropping an *older complete* block for path \(p\) while keeping a *later complete* block does not change \(V\). Length-based dropping can remove the last complete block for some path and break proofs.

**Retention rule.** For each normalized path \(p\), let blocks be ordered by message index and in-message order. Keep the **last complete block** for \(p\). Under dial `first_last` (confirmatory configuration), also keep the **first** complete block for \(p\); intermediate complete blocks are replaced by a fold marker that contains neither `FILE:` nor a code fence, so the extractor will not re-match them. Non-assistant messages and messages without complete `FILE` blocks are unchanged.

**Relation to VSO.** Phase A and phase B share `full_files_in_messages`. If \(P(H)\) retains the last complete block per path relative to \(H\), then \(V(P(H) \oplus \mathcal{M}_{\mathrm{new}}) = V(H \oplus \mathcal{M}_{\mathrm{new}})\) for the path map that omits only intermediate versions—hence omission authorization and pre-send checks see the same file map as without projection (subject to the assumptions in §3.5).

**Cost.** S1 is a single scan of assistant contents with regex matching and a path dictionary; no LLM calls. Savings appear as fewer repeated file bodies in history (fold markers are short).

### 3.5 Projection Preservation Argument

**Extractor.** \(V = \) `full_files_in_messages`: iterate messages in order; for each complete assistant `FILE` block (and applicable context blocks), set \(V[\mathrm{norm}(p)] = \mathrm{body}\). Later assignments overwrite earlier ones.

**Projection \(P\).** For each path, delete (replace with non-matching marker) every complete assistant `FILE` block except the last (and the first, if `first_last`). Leave all other message parts intact.

**Proposition (constructive, limited).**  
If every path’s retained set under \(P\) includes the last complete block occurring in \(H\) for that path, then  
\[
V(P(H)) = V(H).
\]

**Proof sketch.** \(V\) depends only on, for each path, the body of the last complete block in scan order. \(P\) preserves that block and may only remove strictly earlier complete blocks for the same path, which \(V\) would have overwritten anyway. Markers are outside the block grammar. ∎

**Scope.** This is an argument **relative to this extractor and retention rule**, not a theorem over arbitrary parsers or unstructured text. Empirically, offline replay on 504 episodes / 2808 steps reports **0** mismatches in \(V\) and in pre-send check fields; unit tests assert extractor equality and that the projection module does not write into the verifier module. Finite replay ≠ formal verification for all inputs. S1 can still lose non-extractor information (discarded intermediate bodies are gone from the transcript even if the latest body remains).

### 3.6 Complexity and Limitations

- **S1:** one pass over assistant message strings; time linear in history characters; space \(O(\#\text{paths})\) for the keep set.
- **VSO:** one extraction over \(\mathcal{M}_t\) plus hash of each checked body; linear in final message size.
- **Extra prompt overhead:** fold markers and optional S2 lines are small relative to dropped full files (empirically S1 reduces history characters by ~27% on the 504-episode replay corpus before API accounting).
- **Parse limits:** only complete fence-form `FILE` blocks are projected; malformed output is left as-is (and may still fail format checks elsewhere).
- **Concurrency:** no lock between phase-B check and HTTP send.
- **Semantics:** file hash equality ≠ requirement satisfaction (wrong symbol, partial edit, or unrelated churn can still close naive obligation heuristics—another reason S2 is not claimed as correct completion detection).

## 4. Experimental Setup

### 4.1 Research Questions

- **RQ1 (cost):** Does visibility-constrained selective delivery plus S1 reduce per-episode prompt tokens versus a selective-delivery baseline without projection?
- **RQ2 (capability):** Does the projected system remain non-inferior in ESR (margin −12pp)?
- **RQ3 (verification):** Under controlled delivery faults, does VSO detect unsafe omissions and fall back without unsafe ships?
- **RQ4 (robustness):** Do primary directions hold across two model families and under archetype-cluster resampling?

### 4.2 Models and Tasks

| Item | Primary (confirmatory) | Replication |
|---|---|---|
| Model | `deepseek-v4.1-flash-1017` | `qwen3-coder-flash` |
| Decode | temperature 0, seed 0, max_tokens 2048 | same |
| Endpoint | OpenAI-compatible MaaS endpoint (key via env only) | same |
| Tasks | 56 (48 independent + 8 dose) micro-repo multi-step edits | identical task set |
| Structure | 24 archetypes × 2 variants + 8 dose tasks | same |
| Arms (main) | 7 × 3 reps = 1176 episodes | 1176 episodes |
| Focus arms here | **F**, **PROJ** (F+S1), **SAH** (F+S1+S2 aux ledger) | same IDs |

**Baseline F** (`vam_coder_v1.2_F`): selective delivery with visibility proofs, full history retention (no S1/S2).  
**PROJ:** F + S1 only.  
**SAH:** F + S1 + S2 ledger lines (auxiliary; not a separate core claim).  
External same-batch arms: **TRUNC** (paired sliding window, 1300 chars/step), **SUMM** (same-model summarizer; summarizer prompt tokens included in prompt accounting; output sanitized), **RETR** (BM25 top-3, always keep latest). These are *reimplementations*, not original author code.

Primary success metric: ESR (frozen step evaluator). Cost: mean prompt tokens per episode. Non-inferiority margin: **−12pp** on ESR.

### 4.4 Fault-Injection Design (VSO)

Phase 1: 31 deterministic scenarios (13 unsafe/omission negatives, 10 safe positives including boundary, 8 false-block controls) comparing VSO to content-hash (B1) and “was ever sent” cache (B2) baselines under identical faults. Phase 2: 10 frozen scenarios × 3 reps embedded in a real runner via test-side monkeypatch (production code unchanged), DeepSeek.

Metrics (frozen): UOR (unsafe omission rate), SOR (safe omission rate), FBR (false block rate), FSR (fallback success), EDR (detection rate on visibility faults), exclusive detection count on scenario V4 (content unchanged and previously sent but absent from final messages).

## 5. Results

### 5.1 Base Selective Delivery (P1, 720 episodes)

On the P1 task set, F reduced mean prompt/episode by **23.6%** vs memory_off and **24.2%** vs symbol_full_read (paired task bootstrap; Holm p = 0.0002 on both prompt comparisons). ESR differences were −0.8pp with CI lower bounds −4.2pp and −5.4pp (both ≥ −12pp → non-inferior PASS). Family-level sensitivity: 8/8 parameterized families same sign. This establishes the cost–capability frame for later arms; it is not itself an S1 result.

### 5.2 Mechanism Attribution (P2, 1680 episodes)

Disabling the omission/reuse path (`no_oprime`) increased prompt by **397.6 tokens/episode** (CI [−524.8, −275.4] for F − no_O′) with ESR difference CI crossing zero. History redaction saved tokens but reduced visible-context recall (CMR_visible). Must-closure ablation was small (~+24 tokens for keeping closure). **Omission/reuse is the dominant cost lever in the baseline**; S1 later attacks *history redundancy* on top of that delivery machinery.

### 5.3 VSO Controlled Fault Injection

| Stage | Result |
|---|---|
| Phase 1 (31) | UOR=0, SOR=1.0, FBR=0, FSR=1.0; joint PASS |
| Mechanism contrast (V1–V5) | EDR: VSO 1.0, B1 0.0, B2 0.8; **exclusive VSO detection = 1 (V4)** |
| Phase 2 (10×3=30) | decision accuracy 30/30; **unsafe_ship=0; DHO=0** |

V4 is the discriminating case: identical content hash exists and was once sent, but the block is absent from the final messages—B1/B2 authorize; VSO blocks and forces full delivery. **Interpretation limit:** results support verification under *controlled* injections, not production natural-fault rates or universal safety.

### 5.5 External Baselines (same batch)

- **TRUNC** is cheapest on pure prompt (2456 / 2347) by discarding oldest history without a delivery proof; SAH is non-inferior to TRUNC on ESR but not cheaper on prompt.
- **SUMM** becomes *more expensive* in total prompt accounting once summarizer costs are included (5006.5 vs F 3747.5 on DeepSeek, +33.6%); SAH is significantly cheaper than SUMM.
- **RETR** sits between F and SAH on prompt; SAH−RETR is descriptive (CI excludes 0) but not a Holm-gated primary claim.

### 5.6 Cross-Model Stability (RQ4)

Directions match on both models for all primary pairs above. Absolute ESR levels differ (DeepSeek F 0.649 vs Qwen F 0.512); we report models separately and do not pool absolute tokens/ESR. Replication criterion (direction + non-inferiority) holds.

### 5.7 Archetype-Cluster Sensitivity (post-hoc)

Resampling **32 clusters** (24 archetypes × 2 tasks + 8 dose singletons) with B=5000:

- All four prompt CIs remain strictly below 0 (e.g., DeepSeek SAH−F [−977, −317]).
- All ESR non-inferiority lower bounds remain ≥ −12pp (tightest ~ −9.6pp for DeepSeek PROJ−F).
- Leave-one-archetype-out: no prompt sign flips; no non-inferiority failures.
- Task-level bootstrap **underestimates** prompt CI width by roughly 1.34–1.39×; ESR widths are nearly unchanged.

This analysis is **sensitivity only**, not a replacement for the preregistered task-level tests.

### 5.8 Supporting and Negative Evidence (disclosure)

- **S1 replay:** 504 episodes / 2808 steps, extractor and pre-send field equality failures = 0.
- **Dual-token special:** 960 episodes; independent contribution **not** supported (Holm p≈0.109 on prompt; ESR non-inferiority failed under frozen rules; control arm lacked VSO). Excluded from contributions.
- **Related channels (CR/ICG):** independent-set prompt delta ≈ −1.4% with CI including 0 → no claimed gain (motivation for moving effort to history, not a positive result).
- **Protocol violations:** 51/51 attributed EMPTY_TRUNC at max_tokens=1024/2048 eras; controlled 4096 retest resolved 44/51 (86.3%) in isolation without modifying frozen data.

## 6. Discussion

### 6.1 What the evidence supports

Under the frozen protocol, **verifiable selective delivery + path-based history projection** reduces prompt tokens by roughly 17–19% versus the same delivery stack without projection, with ESR non-inferior at −12pp on two models. VSO’s value relative to naive hash/cache checks is demonstrated on the V4 class of faults (visible in history cache logic, absent from the final body). S1’s preservation property is consistent with shared-extractor design and large offline replay.

### 6.2 What the evidence does not support

- Universal safety of selective delivery or production failure rates.
- Formal verification of S1 for arbitrary message languages.
- S2 as correct semantic completion detection or as the source of SAH’s savings.
- Dual-token independent gains.
- KV-cache / latency / memory savings (no tensor measurements).
- ESR *superiority* of PROJ (DeepSeek shows a non-inferior but negative point estimate).
- Generalization to arbitrary repositories, models, or agent scaffolds beyond the tested setup.

### 6.3 Limitations

1. **Synthetic micro-repos** — not full SWE-bench or industrial monorepos.  
2. **Two model families** — direction consistency is not a random-effects meta-analysis.  
3. **Task archetypes** — cluster sensitivity widens prompt CIs; design still shares templates within archetype.  
4. **Temperature 0 is not bit-deterministic** on hosted APIs; repeats act like near-samples; effective unit is task.  
5. **TOCTOU** — no lock between check and HTTP send.  
6. **S2** — optional heuristic with known false-close modes; kept out of the contribution list.  
7. **External baselines** — reimplemented approximations.

### 6.4 Practical guidance

If deployment requires *proof that omitted files are still in the request*, use a VSO-style final-message gate. If the transcript is dominated by repeated full-file rewrites, apply S1-style path projection *before* proof extraction so savings and verification share one visible map. Do not replace delivery checks with summarization alone when total cost includes the summarizer.

---

## 7. Conclusion

We presented **verifiable context reuse** for multi-turn coding agents as the combination of (1) **VSO**, a final-messages visibility and version-consistency gate with fail-closed fallback, and (2) **S1**, a path-normalized projection of complete history `FILE` blocks that preserves the extractor map VSO uses. On preregistered DeepSeek and Qwen experiments, projection cut mean prompt tokens by **16.9%** and **18.6%** respectively while keeping ESR within a −12pp non-inferiority margin; controlled injections showed VSO catching unsafe omissions with zero unsafe ships in phase 2; offline replay found no projection-preservation violations; and archetype-cluster resampling did not reverse primary conclusions. Scope is deliberate: delivery verification under controlled faults, not universal safety; constructive preservation under a specified extractor, not formal verification; prompt-token savings, not latency or KV-cache claims. Future work may tighten obligation state models and evaluate on larger real repositories—without reopening the frozen confirmatory batches reported here.
