### C.1 已证实的基线语义偏差（非隔离破坏，但必须写进结论）

1. **多轮历史对“记忆”语义的稀释**：四基线都保留同一 episode 内的
   对话历史（assistant 轮包含其自己写过的文件全文）。因此
   “fixed_summary 无源码”只对**我们装配的上下文**成立；模型仍可能从
   历史轮看到自己先前写过的源码。证据：rename 最终轮 `fixed_summary`
   step2 通过（`20261016_194913`，`steps/step2/response.txt` 在历史基础上
   增量修改）。该基线失败模式仍成立（trap 0/2），但其“信息饥饿”程度
   被历史部分补偿——解释结果时必须声明。
2. **REUSE_KV 省略与文件级 EXPAND 的交互**：同文件内只要有一个符号
   EXPAND，整文件进入上下文，其余 REUSE_KV 符号不计入 `reuse_omitted`。
   例：rename 最终轮 vam step2，`compute_double` 决策为 REUSE_KV 但
   `helper`（同文件）stale→EXPAND，`reuse_omitted=0`（`per_step.csv`）。
   这是设计使然（按文件去重），但会使 `reuse_omitted` 系统性偏小。

### D.4 对核心假设的直接含义（保守）

1. **token**：vam_coder 累计 prompt tokens **高于** memory_off（2098 vs 1957）。
   在玩具仓库 + 多轮历史协议下，REUSE_KV 文本省略（全部 6 步合计仅
   `reuse_omitted=1`）不足以抵消 step1 全量回退 EXPAND 与更长的模式
   说明文本。**首轮数据不支持“减少输入 token”的假设方向。**
2. **延迟**：模型耗时中位数差异（memory_off 1203ms vs vam 702ms）
   **不能**解释为方法收益——无 prefill/generation 拆分、无 cached_tokens、
   基线执行顺序固定（memory_off 永远最先、vam 最后）、首次调用普遍更慢
   （如 `194629` memory_off step1 t_model=1463ms vs step2 511ms）。
   token 下降 ≠ 延迟下降，此处连 token 也未下降。
3. **成功率**：vam_coder 与两个“给源码”基线同为 5/6，唯一失败是
   inventory step2（模型能力上限，见 E）。fixed_summary 1/6 暴露过期记忆
   的质量风险——这是本轮**唯一**清晰的机制对照差异（trap：fixed 0/2 vs
   vam 2/2）。
4. **系统开销**：P0 sync/route/assemble 中位数 1–10ms，相对 0.3–1.7s 的
   端到端可忽略；这是本轮为数不多可以稳健陈述的工程事实（小仓库）。

## E. 典型成功与失败案例的完整因果链

### E.1 成功：trap × vam_coder（过期摘要陷阱被失效机制拦截）

运行 `20261016_194723`，`episodes/stale_summary_trap/vam_coder/`：

1. **初始**：`pricing.py`（`UNIT = 10`，docstring 含 “(=10)”）、`discount.py`。
2. **step1 路由**（`logs/decisions.jsonl`）：`price`/`total` 均 valid →
   `REUSE_KV`（`sim://kv/…` 模拟指针）。对话历史为空 → 装配层按代理规则
   回退为全文件 EXPAND（`steps/step1/context.txt` 含两个 FILE 块；
   `reuse_omitted=0`）。模型写入 `UNIT = 12`，step1 测试 3 passed。
3. **step2 sync**（`logs/invalidation_events.jsonl`）：
   `content_stale` on `price`（源码哈希≠记忆依据）；
   `dependent_unverified` on `total`（依赖闭包深度 1 ≤ 2）。
4. **step2 路由**：`price`→EXPAND(stale)、`total`→EXPAND(unverified)；
   `REUSE_KV` 被禁止——**未**发生错误复用。
5. **step2 上下文**：包含 `pricing.py` 当前全文（`UNIT = 12` 可见）。
6. **模型输出**（`steps/step2/response.txt`）：`fast_price` 写死 `qty * 12`。
7. **评测**：`eval_output.txt` 4 passed。
8. **对照 fixed_summary**（同 run）：冻结摘要仍称 “(=10)”，step2 把
   `fast_price` 写进错误文件且未写死单价 → 0/2。

### E.2 成功：rename × vam_coder（墓碑 + 依赖失效）

运行 `20261016_194913`：

1. step1：`compute`→`compute_double` 重命名后，sync 记录
   `tombstone compute`、`insert compute_double`、`content_stale helper`、
   `dependent_unverified run`（invalidation JSONL）。
2. step2 路由：`compute`→**DROP**(tombstoned)、`helper`→EXPAND(stale)、
   `run`→EXPAND(unverified)、`compute_double`→REUSE_KV。
3. 旧符号 `compute` 未进入上下文（DROP），未被当作可复用对象。
4. 测试 3 passed。

### E.3 失败：inventory step2 × 全部“给源码”基线（模型能力，非链路）

运行 `20261016_194629`：vam 正确 EXPAND 了 `available`(stale) 与
`can_fulfill`(unverified)，并省略 `catalog_value`（REUSE_KV，`reuse_omitted=1`）。
但模型输出 `return max(stock - reserved, 0)`——加了 `BUFFER = 5` 却未使用。
memory_off / symbol_full_read / vam_coder 三者 step2 同败；symbol_full_read
甚至输出 `NO_EDIT`（`steps/step2/response.txt`）。结论：1.5B 对该指令的
遵循失败，**不能**归因于记忆机制。

### E.4 失败：fixed_summary 的过期记忆模式（trap + inventory）

trap step1：无源码时模型直接编造 `class Stock`（inventory，`194629`）或
写错文件（trap step2 写进 pricing.py）。这是该基线设计要暴露的失败模式，
同时说明 1.5B 在“只有摘要”时行为高度不可靠——用它度量“过期记忆代价”
时，失败可能是“无源码”与“过期”两个因子的混合（见 G 节可能问题）。

### E.5 评测口径修正的因果（非方法因素）

- `194440` → `194629`：inventory step1 原断言 `available(2,5)==0`，
  与该步“纯减法”语义矛盾（`assert -3 == 0`，见旧轮 eval_output）。
  修正为 `== -3` 后同代码通过。
- `194812` → `194913`：rename step2 原断言 `run(4)==9`，正确值为 10
  （`helper(4)=4*2+2`）。修正后同代码通过。
- 修正前后两轮均保留；**修正依据是任务语义，不是某方法的表现**——
  两处修正均使原先失败的多方法同时转为可通过（memory_off 与 vam 同步
  变化），可排除“为单一方法放水”。但流程缺陷成立：判据修改未版本化
  （见 G-已证实-3）。

## F. 测量口径、日志一致性、缓存/热身偏差

### F.1 计时边界（源码核对 `run_p1.py`）

| 计时字段 | 边界 |
| --- | --- |
| `t_sync_ms` | `InvalidationManager.sync()` 调用墙钟 |
| `t_route_ms` | `route_repo()` 调用墙钟 |
| `t_assemble_ms` | 上下文装配函数墙钟（不含写盘） |
| `t_model_ms` | HTTP 发出 → 全量回包读完（**含**网络 + 服务端排队 + prefill + generation） |
| `t_eval_ms` | 临时目录 pytest 子进程 |
| `t_step_ms` | 步内合计（不含 episode 级初始 sync 的真实发生时刻） |

已证实的口径缺陷：

1. **初始 sync 双重记账不一致**：episode 级初始 sync 发生在步计时器
   之外。对 symbol_full_read / vam_coder，步内又 sync 一次且 `t_sync_ms`
   被步内值**覆盖**（初始成本从 CSV 消失）；对 fixed_summary，
   `t_sync_ms` 取初始值但计入“步和”会**超过** `t_step_ms`（实测 gap
   约 −12~−15ms，5 处，全为 fixed_summary step1）。影响很小但口径不自洽。
2. **无 prefill/generation 拆分**：`t_model_ms` 是混合量，不能当推理速度。
3. **token 字段**：优先取 API `usage`（40 步真实运行 `usage_source=api`，
   无估算污染）；但 `raw_usage` 未落盘，`cached_tokens` 丢失。
4. **路由 `est_tokens` 未校准**：router 用 chars/4 估算记忆块
   （inventory vam step2：est 合计 95，仅覆盖装配块），而实际
   `prompt_tokens=366` 含系统提示、历史与任务文本。二者不可直接比较，
   目前也未做校准实验。

### F.2 热身 / 顺序偏差

- 5 个真实 run 共用一个 llama-server 进程；每个 episode 内基线顺序恒为
  memory_off → symbol_full_read → fixed_summary → vam_coder。
- 首步模型耗时普遍高于次步（如 trap memory_off 1230→1177ms；
  rename memory_off 1618→578ms），呈典型热身形态。
- 结果：memory_off 的延迟被系统性高估的可能性存在；**任何跨基线延迟
  比较在本轮数据中都不可信**。

### F.3 确定性

同参数（temp=0, seed=0）跨 run 抽查 2 组 response 字节级一致
（rename memory_off step1、inventory vam step2）。样本少，只能说
“初步显示可复现”，不能证明服务端完全确定性。

### F.4 日志一致性

- decisions.jsonl 的动作与 `per_step.csv` 的 E/R/C/D 计数、
  `result.json` 的 decisions 字段三者一致（抽查 trap/inventory/rename
  vam_coder 全部 6 个真实步）。
- invalidation JSONL 事件与最终 store 快照一致（inventory vam 最终：
  `available` stale v2、`can_fulfill` unverified、`catalog_value` valid）。
- 无相互矛盾日志。

## H. 是否具备扩展正式任务集（P1-v1.0）的条件

### H.1 结论

**有条件具备**——测量链路与基线隔离的工程骨架已经成立，但必须先完成
一组“阻塞项修复”（见阶段三优先级），否则扩大任务集只会放大口径缺陷。

### H.2 支持扩展的证据

1. 64/64 步产物完整，0 缺失；四基线状态隔离正确；无测试泄漏。
2. 版本感知机制端到端可观察：stale/unverified/tombstone → EXPAND/DROP
   与日志、上下文、最终 store 三者一致（E.1/E.2）。
3. 评测隔离（临时目录 + PYTHONPATH）有效；失败输出可追溯。
4. 同参数重跑 response 一致（2/2 抽查），初步可复现。
5. 系统开销测量可用（毫秒级，量级清楚）。

### H.3 扩展前必须满足的门槛（阻塞项）

1. 判据冻结可审计：eval 目录哈希 + 脚本哈希写入 run_meta；修正判据必须
   新版本号，禁止静默覆盖。
2. P1 代码入 Git（新分支/提交），run_meta 记录 P1 commit。
3. 环境元数据补全：server 版本、模型文件哈希或量化标签、ctx、硬件。
4. `raw_usage`（尤其 cached_tokens）落盘；计时边界文档化并修正初始
   sync 记账。
5. 历史策略显式化：定义“会话历史是否属于上下文预算/记忆比较范围”，
   并在四基线中一致执行或明确不对等的理由。
6. 执行顺序轮换 + 每 episode×基线重复 ≥3 次（不同 run 目录）。
7. 修正 fixed_summary 与“过期摘要”因子的混淆设计（G.2-1）后再解释
   trap 类结果。

### H.4 明确不支持的结论（本轮及可预见的玩具集扩展前）

- 不支持“VAM-Coder 优于基线”的任何表述。
- 不支持真实 KV Cache 加速或显存收益。
- 不支持基于 p95/中位数的延迟优势结论。
- 不支持统计显著性。
